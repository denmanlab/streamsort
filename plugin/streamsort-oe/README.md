# Streamsort — Open Ephys plugin (Phase 2b)

A **Processor plugin** for the Open Ephys GUI (v1.x, Plugin API v10). It runs streamsort's online
spike decoder on **any number of data streams** and publishes the decoded spikes, stimulus-pulse
onsets and stim TTLs over **ZMQ** to the streamsort worker. No Python runs inside the GUI, and no
Python Processor or ZMQ Interface node is needed.

The decoding code is the JUCE-free C++ core in `cpp/core/` (shared with the Python module `streamsort_core`).
On jlh32 replays it produces spike sets **identical** to the validated Phase 1 Python decoder.

## What it does

| | |
|---|---|
| Input | any continuous streams in its signal chain (e.g. Neuropix-PXI Probe A/B/C AP) |
| Per stream (editor) | **enable** checkbox (stream selector), **Kilosort folder** button, status line (`248/327 units, 200 ch`) |
| Processor-wide | stim TTL stream + line, ZMQ publish port (5557), condition port (5558), decoder threads per stream (2) |
| Decoding | one thread per enabled stream: µV → raw counts (`round(x / bitVolts)`, exact), artifact suppression (condition-keyed templates + bridging), causal 300 Hz high-pass, median reference, banded whitening, detection, template matching |
| Output | ZMQ PUB (spikes per block, pulses, stim TTLs, hello); the GUI data pass through **unchanged** |
| Input from worker | ZMQ SUB: condition id of the next pulse (artifact-template key) |
| Hot-swap | the bank is reloaded when `decoder_tables.txt` changes (atomic writes), ≥ 0.6 s after the last pulse; artifact history is kept |

`process()` only copies each enabled stream's block, converted to counts, into that stream's queue and returns.
Decoding never runs on the GUI's signal-chain thread. If a decoder falls more than 2000 blocks behind,
the oldest block is dropped and counted; the count is logged at stop.

## Kilosort folder → decoder bank

The folder button accepts **any Kilosort output folder**. The plugin loads `<folder>/streamsort/` (or the folder itself
if it holds `decoder_tables.txt`). Build that subfolder once per sort with the Python package:

```
streamsort bank --ks-folder <kilosort sorter_output> --rec-dir <.../Record Node N/experiment1/recording1> \
                --stream Neuropix-PXI-104.ProbeA-AP --nch 200
```
`streamsort fit` / `streamsort watch` write the same subfolder automatically. Contents: `*.npy` tables +
`decoder_tables.txt` (scalars, sample rate, unit counts, signal-path fingerprint), plus `templates.npz`,
`whitening.npz`, `sorting_report.csv`, `bank_info.json`. The plugin refuses a bank whose sample rate differs from the
stream's by more than 1 %, or that needs more channels than the stream has.

## ZMQ messages (published on `tcp://*:<zmq_port>`)

Each message uses the Open Ephys ZMQ Interface framing: `[envelope][JSON header][binary payload]`.
Spikes are **batched**: one message per stream per block, not one per spike.

| envelope | header `type` | fields | payload |
|---|---|---|---|
| `STATUS` | `hello` | stream, stream_id, sample_rate, n_channels, bank, fingerprint, unit_ids[] (usable), t_wall_us; at start, every 2 s, and after a hot-swap | — |
| `SPIKES` | `spikes` | stream, stream_id, message_num, n, head (last sample + 1), sample_rate, t_wall_us | n×int64 sample numbers, then n×int32 unit ids (n = 0: heartbeat) |
| `PULSE` | `pulse` | stream, onset_sample (−1 = TTL with no detected artifact), ttl_index (−1 = no TTL source), t_wall_us, approx | — |
| `EVENT` | `event` | stream, line (1-based), state, sample_num, timestamp_s, ttl_index, t_wall_us | — |

Worker → plugin, on `tcp://127.0.0.1:<cond_port>` (the worker binds PUB, the plugin connects SUB):
`[CONDITION][{"type":"condition","id":N}]`.
`t_wall_us` is microseconds since the Unix epoch on the acquisition PC. The worker compares it with its own clock,
which is valid on the same machine. Python reference implementation: `streamsort/worker2/protocol.py`.

**Pulse pairing.** The exact onset comes from artifact clip detection. The stim TTL (which sits about 0.4–0.6 ms off the
artifact) supplies the trial index that aligns pulses across streams. Pairing uses the block arrival time, which is
shared by all streams of one `process()` call, with a 50 ms tolerance:
- a clip with no TTL is dropped;
- a TTL with no clip is sent with `onset_sample = -1`.

With `stim_line = 0`, every clip is published with `ttl_index = -1`.

## Build

The plugin needs the Open Ephys GUI **source at the tag of the installed GUI** (`v1.1.0` was used here) and libzmq.
libzmq builds for macOS, Windows and Linux ship in `libs/` (copied from `open-ephys-plugins/zmq-interface`; libzmq is MPL-2.0).

```
git clone --branch v1.1.0 https://github.com/open-ephys/plugin-GUI.git
# JuceHeader.h is generated by the GUI's own CMake configure; either configure the GUI once, or:
#   sed -e 's/@GUI_VERSION@/1.1.0/' -e 's/@GUI_VERSION_HEX@/0x010100/' \
#       plugin-GUI/JuceLibraryCode/JuceHeader.h.in > plugin-GUI/JuceLibraryCode/JuceHeader.h
```

**macOS (arm64 or x86_64)**
```
cmake -S plugin/streamsort-oe -B plugin/streamsort-oe/build -DGUI_BASE_DIR=/path/to/plugin-GUI -DCMAKE_BUILD_TYPE=Release
cmake --build plugin/streamsort-oe/build -j
cmake --install plugin/streamsort-oe/build    # -> ~/Library/Application Support/open-ephys/plugins-api10 (+ libzmq in shared-api10)
```
Build for the architecture of your GUI (`-DCMAKE_OSX_ARCHITECTURES=arm64` for the Apple-silicon GUI).
The bundle links libzmq through `@rpath` → `shared-api10`.

**Windows x64 (rig)**: Visual Studio 2022, and a GUI build tree that contains `Build/Release/open-ephys.lib`.
That means the GUI must be built from source once, as for every Open Ephys plugin on Windows.
```
cmake -S plugin/streamsort-oe -B plugin/streamsort-oe/build -G "Visual Studio 17 2022" -A x64 -DGUI_BASE_DIR=C:/src/plugin-GUI
cmake --build plugin/streamsort-oe/build --config Release
cmake --install plugin/streamsort-oe/build --config Release   # -> <GUI>/Build/Release/plugins + libzmq dll in shared
```
The core is compiled with `/fp:precise` (MSVC) or `-ffp-contract=off` (clang/gcc). This keeps the arithmetic identical
to the validated reference: no FMA contraction, no fast-math.

## Rig checklist (steps not yet run on hardware)

1. **Stim TTL inside the plugin's chain.** A processor only sees events from streams that pass through it. Merge the NI-DAQ
   source (or whichever source records the stim trigger) into the Neuropix-PXI chain with a **Merger**, upstream of
   Streamsort. Then select that stream and line (1-based, e.g. 5) in the editor.
2. Enable each probe AP stream in the stream selector and point **Kilosort folder** at its sort. The status line must show
   units (for example `248/327 units, 200 ch`).
3. Start the worker (`streamsort worker-gui` or `streamsort worker-zmq --config …`), preferably before pressing play.
   The plugin repeats `hello` every 2 s, so a worker that joins late picks up the streams within 2 s.
   It analyses only pulses that arrive after it joined.
4. Ports 5557/5558 must be free. On Windows, allow `open-ephys.exe` and Python through the firewall for localhost,
   or keep everything on one machine (the defaults are already localhost-only for the condition port).
5. Threads: about 2 per stream on 8 cores. Check at the first stop that no blocks were dropped (log line).
6. Verify once on the rig: spikes on the GUI clock (sample numbers) match a short offline replay of the same recording
   (`streamsort emulate`).
